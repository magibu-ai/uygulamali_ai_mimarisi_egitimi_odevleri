# CLAUDE.md

## Project Overview

This project implements a Turkish medical document retrieval and RAG system for an academic assignment.

The system must:

1. Select 100–1,000 Turkish medical articles from a Hugging Face dataset.
2. Split article text into meaningful chunks.
3. Generate embeddings for each chunk.
4. Store chunks, metadata, and vectors in a vector database.
5. Retrieve relevant chunks using cosine similarity.
6. Use a similarity threshold to reject questions whose answers are not present in the document collection.
7. Evaluate retrieval behavior using exactly 30 benchmark questions:
   - 20 positive questions
   - 10 negative questions

8. Produce reproducible evaluation results and documentation.

## Core Technologies

- Python
- Hugging Face Datasets
- sentence-transformers
- ChromaDB
- NumPy
- pytest

The final LLM/RAG answering layer is secondary. Retrieval correctness and threshold behavior are the primary objectives.

## Dataset

Use one of:

- `umutertugrul/turkish-medical-articles`
- `umutertugrul/turkish-hospital-medical-articles`

The selected dataset and filtering strategy must be documented.

## Vector Record Schema

Every stored chunk must contain at minimum:

- `url`
- `chunk_text`
- `chunk_vector`

Recommended metadata:

- `title`
- `parent_id`
- `source`

## Chunking Requirements

The chunking implementation must be deterministic and reproducible.

The selected strategy must be documented in README.md.

A recommended strategy is:

1. Split documents using paragraph boundaries.
2. Preserve meaningful paragraph structure.
3. Apply a maximum token limit.
4. Split oversized paragraphs using a token-based fallback.
5. Apply controlled overlap where appropriate.

Do not silently truncate article content.

## Embedding Requirements

Use one embedding model consistently for both:

- document chunks
- user queries

The embedding dimension must be verified programmatically.

Do not mix embeddings generated by different models.

## Retrieval Requirements

Use cosine similarity.

Retrieval must expose:

- chunk ID
- similarity score
- metadata
- chunk text

Use top-k retrieval before threshold filtering.

The threshold must be determined from benchmark results rather than arbitrarily selected.

## Threshold Behavior

If the highest relevant similarity score is below the selected threshold:

Do NOT generate an answer using an LLM.

Return:

"Bu sorunun cevabı dokümanlarımda yer almamaktadır."

Negative benchmark questions must therefore be rejected by the retrieval gate.

## Benchmark

Exactly 30 benchmark questions must be maintained:

- 20 positive
- 10 negative

Positive questions must have answers directly supported by the selected document collection.

Negative questions must not have answers supported by the selected document collection.

Benchmark questions must be reproducible and version controlled.

## Reproducibility

All random dataset selection must use an explicit random seed.

Configuration values must not be hard-coded across multiple files.

Prefer configuration-driven behavior.

## Engineering Rules

- Do not fabricate dataset content.
- Do not fabricate benchmark results.
- Do not fabricate screenshots or evaluation metrics.
- Do not silently change the dataset after benchmark creation.
- Do not change the embedding model without regenerating embeddings.
- Do not change chunking parameters without rebuilding dependent artifacts.
- Validate intermediate outputs after every pipeline stage.
- Prefer small, testable modules over a monolithic script.
- Add tests for critical functionality.
- Keep generated artifacts separate from source code.

## Development Workflow

Work phase-by-phase according to ROADMAP.md.

Before implementing a phase:

1. Inspect the existing repository.
2. Read the relevant roadmap section.
3. Identify dependencies and assumptions.
4. Implement only the current phase.
5. Run tests and validation.
6. Report what changed.
7. Do not continue to the next phase unless explicitly instructed.

## Important

The academic assignment requirements have priority over unnecessary architectural complexity.

Do not add technologies that are not needed for the assignment.
Do not over-engineer the system.
Do not replace working components without a concrete reason.
